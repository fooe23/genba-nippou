# 件の見積書（要［先に出す］・要［後出し］・不要）と「見積提出が必須のお客様」 設計

2026-11-12。利用者との対話（見本 `.superpowers/brainstorm/24602-1794232833/content/issue-estimate-1.html` で確認）で決めた内容。

## 目的（なぜ）

- お客様によっては、追加・変更の工事に入る前に**必ず見積書を出す**約束になっている。いまのアプリは件の状態（見積中・対応中・完了）を自由に変えられるので、見積を出さないまま工事を進めてしまっても気づけない。
- 一方で、雨漏れの応急処置のように**お客様の指示でその場で先にやる**こともある。そのときは止めずに進め、完了の確認（サイン）をもらって、見積は後から出す。後から出すのを忘れないようにしたい。
- 見積の要らない指示（見積を出さない小さな手直しなど）もあるので、件ごとに決められるようにする。

## 決めたこと（利用者 2026-11-12）

1. **現場の設定**「見積提出が必須のお客様」（オン・オフ。現場ごと。管理者が現場の編集で変える）。オンの現場で新しく作る件は、見積書の欄が最初から「要（先に出す）」になる。件ごとに変えられる（見積の要らない指示もある）。
2. **件の欄「見積書」**（3 つから選ぶ）：
   - **要（先に出す）**：見積提出を記録するまで「対応中」「完了」にできない。
   - **要（お客様の指示で先に対応・後出し）**：その場で対応・完了できる。見積を出すまで赤い印が残る。
   - **不要**：見積は出さない。今までどおり自由に進められる。
3. **要（先に出す）で見積提出の記録が無い件**は、状態を対応中・完了にできない（画面でも DB でも止める）。画面には赤い枠で理由を出し、「お客様の指示で先に対応するときは、見積書を『要（お客様の指示で先に対応・後出し）』に変えてください」と案内する。
4. **要の件で見積提出の記録が無い**あいだ、赤い印を出す：
   - 要（先に出す）→「**必須の見積書が未提出**（依頼から N 日）」
   - 要（後出し）→「**見積書が未提出（後出し）**（依頼から N 日）」
   - 出す場所：日報の件の欄（その件を書いた日報）、次の日以降の日報の上の黄色い枠（件のバナー）、現場の画面、追加・変更の一覧。見積提出を記録するまで出続ける（後出しで完了した件も）。
5. **当日依頼・当日対応（後出し）**：「完了」を押すと「お客様に、完了の確認（サイン）をもらいますか？」と出し、「**サインをもらう**」「**あとで**」を選ぶ。サインをもらうは、今あるお客様用の確認画面（その件だけに印を付けて開く）に進む。サインは完了のときの **1 回だけ**（見積を後で出して記録しても、2 回目のサインは求めない）。
6. **日をまたぐ件**：要（先に出す）は見積提出を記録すれば対応中・完了にできる。後出し・不要は自由に進められる。

## 作り手の判断（利用者が読んで直せる）

- **オフの現場の既定**：新しい件の見積書は「不要」（今までと同じ動き。止めない・印も出ない）。オフの現場でも件ごとに「要」を選べる。
- **既存の件**：見積提出の記録がある件だけ「要（先に出す）」、ほかは「不要」にする（SQL で 1 回だけ埋める）。記録がある件は印も出ず止めもしないので、見た目は今と変わらない。
- **新しく件を作るときの状態**：見積書が「要（先に出す）」なら、状態は見積中だけ選べる（対応中は選べない）。行の「＋ この行の件を作る」から作るときも、要（先に出す）なら見積中で作る（DB も、対応中で作られそうになったら見積中にする）。
- **見積書の欄を変えられる人**：社員・管理者だけ（見積提出の記録と同じ）。協力会社のアカウントは件を作れるが、見積書の欄は選べず、現場の設定どおりになる（必須の現場＝要［先に出す］、ほかは不要）。DB も同じ（協力会社が作る件は、渡した値を見ずに現場の設定から決める）。
- **いつでも変えられる**：見積書の欄は、状態・精算・見積提出と同じく、日報が提出済み・承認済みでも変えられる（件の中身の鍵の対象外）。完了した現場では変えられない。
- **止める組み合わせ**（DB の `estimate_required_first`）：
  - 要（先に出す）・記録なしの件を、対応中・完了にする。
  - 対応中・完了で記録なしの件の見積書を「要（先に出す）」に変える（画面では選べないようにする）。
  - 要（先に出す）の対応中・完了の件の見積提出の記録を取り消す（間違えて記録したときは、先に見積書を「後出し」にしてから取り消す。画面にその旨を出す）。
- **完了した後出しの件にも記録できる**：今は完了した件に「見積提出を記録」を出していないが、見積書が「要」の件は完了していても出す（後出しの見積を記録して印を消すため）。
- **「依頼から N 日」**：件を書いた日報の日付（依頼の日）から今日（日本時間）までの日数。同じ日は「依頼の当日」。日報を過去の日付で開いても今日で数える（いまの遅れを知るため）。
- **今までの印との関係**：赤い印が出る件では、今の「見積書なし」（見積中でファイルも記録も無い件）の印は出さない（同じことを 2 回言わない）。「見積書あり」（ファイル）は印を消さない。見積書の PDF を付けただけでは「提出」とみなさない（出した日は「見積提出を記録」で残す）。
- **サインの候補**：今のお客様用の確認画面の候補は「その日報の件＋見積中・対応中の件」なので、前の日に作った件をその日に完了にすると候補から外れてしまう。候補に「**その日に完了にした件**（完了日がその日報の日付）」を足す。
- **サインを勧める条件**：見積書が要（後出し）の件を「完了」にするときだけ。日報が保存済み・まだサインが無い・承認の画面でない・やり直しの件でないときに「サインをもらう」を出す。出せないとき（日報が未保存・もうサインがある）は「あとで」だけと短い理由を出す。完了にしてから確認画面に進む（キャンセルしても完了のまま）。

## 協力会社のアカウント

- 件を作れる（今までどおり）。見積書の欄は選べない（表示だけ「見積書：要（先に出す）」など）。DB が現場の設定から決める。
- **赤い印は見える**（「必須の見積書が未提出」「見積書が未提出（後出し）」と依頼からの日数）。止まる理由が分かるように、状態の札の赤い枠も出す（「社員に見積提出の記録を頼んでください」）。
- 見積書の中身・金額・ファイル・「見積書あり／なし」「見積提出 MM/DD」の印・「見積提出を記録」のボタンは今までどおり見えない。提出の日は渡さない（`hideEstimateFromPartner`）。印に使う「未提出かどうか」だけを、日付を消す前にサーバーで決めて渡す。
- 現場の設定「見積提出が必須のお客様」は管理者の画面にだけ出す（列は読めてよい。お金ではない）。

## やらないこと

- 帳票（PDF・Excel・台帳）・お客様用日報 PDF に見積書の欄や赤い印を足すこと。
- お客様用の確認画面に「お見積りは後日お出しします」などの文言を足すこと（→ 問い）。
- 件の種別（やり直し・客先都合など）で既定を変えること（→ 問い）。
- 見積提出の期限・通知（メール・ホームの一覧の件数）。

## 失敗になること

- 要（先に出す）で記録の無い件が、画面・Server Action・Supabase の API の直接の更新のどれからでも、対応中・完了になる。
- 承認済みの日報・提出済みの日報の件の状態・見積提出が、今まで変えられた場面で変えられなくなる（不要・後出しの件、記録のある件）。
- SQL を実行する前に新しい版のアプリを出すと、件や現場が読めなくなる・件を作れなくなる。
- 協力会社のアカウントに、見積書の中身・金額・提出の日・「見積書あり」の印が見える。
- 後出しの件を完了にしたら、サインを 2 回求められる。

## 制約

- UI は日本語、375px、44px。
- SQL は差分ファイル `supabase/update_2026-11-20_issue_estimate.sql`（何度実行しても安全）。check は名前付き（`_ck`）で、Postgres の列の自動 check 名（`<表>_<列>_check`）と重ねない。`gn_report_issues_guard` を差し替えるときは、今の定義（`update_2026-11-14_estimate_submitted.sql`）をそのまま写して足すだけ。`gn_sites` に列を足すので、列の SELECT を付ける（`update_2026-11-16_site_money.sql` の注意）。作り手は `npm run check:sql` で構文だけ確かめ、データベースでは実行しない。利用者が SQL Editor で実行してからデプロイ。
- 新しい版のアプリは SQL の前でも動く（列が無ければ見積書の欄・現場の設定・赤い印・止める判定を出さず、今までどおり）。
